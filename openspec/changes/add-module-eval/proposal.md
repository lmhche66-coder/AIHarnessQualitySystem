# Proposal

## Why

文章的核心主张是「评测面向架构」：Agent 由感知、规划、记忆、工具四个模块协作运行，评测也应按同样的结构逐层拆解，让每一层的质量可独立观测。平台此前只有按能力层与用例类型的划分，判定只能看到最终的断言通过与否；虽然上一轮加了模块级评测范围与三维记分卡，但模块信号仍要靠人把断言名手工对齐，且没有让 agent 把模块内部信息写进轨迹的通道。

文章给出的机制是运行时的 EvalTrace：Agent 的每个节点在完成自己的工作后，把关键信息写进一条随链路流转的轻量轨迹——感知写命中的 Skill、意图类型与耗时，规划写路由决策与耗时，记忆写注入耗时与会话轮数，工具写调用记录，检索写返回的片段。平台据此做模块级断言，而不是从最终回复文本里反推。

## What Changes

- 新增模块级信号层：把感知、规划、记忆、工具四个模块（检索作为记忆的数据来源单列）的执行信息以 `module.<name>` 事件写入既有轨迹，对运行记录格式零侵入。
- 新增五个模块级断言：感知的意图/Skill 命中、规划的路由决策与工具决策、记忆的短期记忆保留、记忆的长期检索召回。
- 新增上游跳过规则：路由决策失败时，依赖检索证据的下游指标自动标记为跳过，既不计入分子也不计入分母。
- 扩展 bridge 协议：agent 可在响应里上报 `signals`，平台在用例执行期把信号写入当前轨迹，因此模块信号由被测 agent 自己提供，平台不猜。
- 记分卡新增模块聚合：按感知/规划/记忆/工具分组给出指标通过率。
- 修正两处既有缺陷：任务运行先落盘再并入 agent 用量导致 token 丢失；任务耗时用了工具调用跨度而非墙钟耗时。
- **BREAKING**：无。bridge 新增字段可选，轨迹事件名新增而不改动既有命名。

## Capabilities

### New Capabilities

- `core-module-eval`: 模块级信号采集、模块级断言与按模块聚合的诊断。

### Modified Capabilities

- `eval-core`: 过程、任务与对话三类用例的判据新增五种模块级检查类型。
- `agent-bridge`: 响应协议新增可选的模块信号列表。

## Impact

- 新增 `agenteval.modules` 模块；`models`、`process`、`tasks`、`dialogue`、`bridge`、`scorecard` 与 `cli` 做增量改动。
- 新增示例 agent 与模块任务，演示「agent 上报信号 → 平台断言 → 模块记分卡」的完整闭环。
- 依赖无新增；不内置任何模型，模块信号由被测 agent 提供，平台只负责采集、断言与聚合。
- 不做的事：不插桩 agent 内部实现，不替 agent 产生信号；不改门禁与基线口径。
