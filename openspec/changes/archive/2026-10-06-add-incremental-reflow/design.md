# Design

## Context

See proposal.md - Why。`triage.py` 已经实现了正确的回流语义：只对能仅凭轨迹复现的失败产出候选用例，并且**期望沿用原用例**、交付前对证据轨迹自证。缺的不是判定逻辑，而是"持续发现"这一层：入口要求人工给出运行标识，且没有跨运行的记忆。

## Goals / Non-Goals

**Goals:**

- 让回流变成可以被 CI 定时调用的幂等操作。
- 用指纹消除重复项，使数据集保持可用。
- 复用既有归因与自证，不重建第二套判定。

**Non-Goals:**

- 不做自动生成期望：期望一律沿用原用例，否则只会产出必然通过的假用例。
- 不做失败聚类与语义归并，指纹只做精确去重。
- 不做外部数据源的采集连接器；外部样本先经既有导入能力进入运行记录。

## Decisions

### D1 指纹取「用例 + 失败判据的期望与实际」

只用用例标识会漏掉"同一用例换了失败原因"；加入判据的期望与实际，能在精确去重的同时区分不同失败模式。备选：只按用例去重（丢失新失败模式）。

### D2 水位用文件账本，而不是删除已处理运行

运行记录是审计资产，不能因为"已回流"就丢弃。账本单独记录已处理指纹与时间，运行目录保持完整。备选：处理后就地标记运行（污染审计数据）。

### D3 候选标识带指纹后缀

既有候选标识是 `case@repro`，同一用例的第二种失败模式会与第一种撞名。增量回流生成的候选在标识上追加指纹前缀，保证互不覆盖，同时不改动既有 `triage` 的标识。备选：统一加后缀（改变既有资产标识，破坏已有基线引用）。

### D4 数据集只追加

数据集是累积资产，人工可能已经在上面加过用例或调整。整体重写会覆盖人工改动，因此只追加未出现的条目。备选：每次全量重写（丢失人工编辑）。

## Risks / Trade-offs

- [指纹过于精确会导致同一根因的不同实际值被算作不同样本] → 这是刻意的：宁可多留候选让人判断，也不要静默合并掉真实的第二种失败。指纹字段可随需要调整。
- [扫描全部运行在运行数很多时变慢] → 账本让已处理的失败在后续运行中被快速跳过；真正的成本只在首次全量扫描。
- [数据集无上限增长] → 这是待办而非缺陷：候选进入数据集前仍建议人工确认，后续可加清理策略。
