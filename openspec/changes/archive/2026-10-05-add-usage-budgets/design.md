# Design

## Context

- 既有 `trace-assertions` 提供工具调用归一化与判据族；`e2e-tasks` 复用同一判据族；`quality-gate` 消费判定结果。See proposal.md - Why。
- 平台回答得了「做对没有」，回答不了「代价多少」。一个用例可以全绿，同时调用三十次、重试十次。
- 硬约束：指标必须从已有轨迹推导，不引入外部计时器或采样器，否则结论不可重放。

## Goals / Non-Goals

**Goals:**

- 调用次数、重复调用次数、耗时成为一等观测量，并进入判定结果。
- 用例能声明非功能上限，超限即失败，且失败原因可读。
- token 用量能汇总，未上报时如实标注而不是编造。
- 预算失败走既有判定与门禁通道，不新增一套结果格式。

**Non-Goals:**

- 不做吞吐与并发压测，本变更只覆盖单次用例的代价指标。
- 不做显存与推理引擎 benchmark。
- 不做 token 预算判定：用量上报尚未覆盖所有接入方式，先做观测量，避免给出不可信的门槛。
- 不做成本货币化换算，汇率与单价模型留给使用者。

## Decisions

### D1 指标从轨迹推导，而不是外部计时

耗时取自轨迹首尾事件的时间差，调用次数取自工具调用事件数。这样指标与判定同源，重放一份已保存轨迹会得到同样的指标，指标本身也可被回归比对。
备选：用外部计时器与计数器（与轨迹可能不一致，且回放时无法复现）。

### D2 重复调用按「相同目标与相同参数」统计

这正是成本随重试膨胀的形态：agent 一遍遍用同样的输入重试同一个工具。用参数指纹分组后取每组的多余次数求和。
备选：只统计总数（看不出重复）；按调用结果统计（重试与正常多步无法区分）。

### D3 预算与 token 用途分开：预算判成败，token 只做观测

token 用量依赖接入方主动上报，覆盖不全时把它做成门槛会误伤。因此 v1 只把 token 作为观测量汇总，并在未覆盖时明确标注；等上报可靠后再引入 token 预算。
备选：立刻做 token 预算（覆盖不全时门槛不可信，容易被绕过）。

### D4 预算判据复用既有判据族

预算判据与顺序、恢复、终态判据并列，走同一套 `CheckOutcome` 与 `Verdict`，因此运行记录、门禁、失败回流、回归比对全部零改动即可覆盖。
备选：另建一套预算结果（重复实现判定、存储、门禁与回流）。

### D5 耗时分位数用最近秩法并明示口径

分位数没有唯一定义，不同算法在小样本上差异明显。采用最近秩法（取排序后第 `round(f * (n - 1))` 个值），并在报告中写出口径，避免读者按别的定义理解数字。
备选：引入 numpy 计算（新增依赖，且不同实现的分位数口径仍然需要说明）。

### D6 token 用量的承载位置是工具结果

模型调用在本平台的接入形态里通常包在工具或适配器之后，因此把用量放在工具结果上不需要改动 agent 协议。没有模型调用的工具保持为空，不影响任何既有行为。
备选：改 agent 协议传入上报句柄（破坏既有 agent 实现）。

## Risks / Trade-offs

- [轨迹首尾时间差不等于端到端耗时] → 它衡量的是工具调用跨度，不含模型思考时间；该口径在文档与报告中写明。
- [token 覆盖不全时容易误读为总消耗] → 运行时明确标注覆盖情况，未覆盖就写未覆盖。
- [重复调用的判定粒度依赖参数相等] → 参数不同就不算重复，这是有意为之，避免把正常多步误判为膨胀。
- [预算阈值可能被随意放宽] → 阈值来自用例定义并进版本控制，修订会体现在 diff 里，而不是藏在代码里。

## Migration Plan

- 判定结果与运行记录新增可选字段，旧记录仍可读取；既有用例不声明预算则行为不变。
- 回滚：移除预算判据与指标字段，既有判据族与运行格式不受影响。
