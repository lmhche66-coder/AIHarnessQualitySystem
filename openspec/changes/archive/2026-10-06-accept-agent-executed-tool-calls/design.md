# Design

## Context

See proposal.md - Why。`agent-bridge` 的 `Tool execution modes` 已经声明两种模式，但 `BridgeAgent.for_task` 在 agent 模式下直接抛错，理由是平台没有渠道把「agent 已经执行过的调用」写进轨迹——轨迹此前只由平台侧的工具包装器写入，而那种写入必然伴随一次真实执行。

## Goals / Non-Goals

**Goals:**

- 让自带工具与审计的 agent 能接入 task 能力，并保留过程断言。
- 让「平台执行」与「agent 执行」两种归属在同一个能力下并存。
- 用一个真实后端验证这条路径。

**Non-Goals:**

- 不做跨进程的轨迹合并协议，agent 回报什么就记什么。
- 不改动平台执行模式的语义与既有任务行为。
- 不把具体系统的适配逻辑写进平台内核。

## Decisions

### D1 用上下文暴露当前轨迹，而不是给 AgentRunner 加参数

改 `AgentRunner` 签名会破坏全部既有接入方与测试。用 `contextvars` 暴露当前用例轨迹，适配器在有需要时读取，既有调用方零改动。备选：扩展协议签名（破坏兼容）。

### D2 按工具模式分派，而不是按能力分派

task 的两种模式对应两种现实：评测提供环境（平台执行）与 agent 自带工具（agent 执行）。按 `tool_mode` 分派让同一条 CLI 路径服务两类接入方。备选：为 agent 执行模式单开命令（重复且易配错）。

### D3 具体系统的适配逻辑放在 `bridges/`，不进内核

PhysioAIOps 的认证、会话、SSE 与审计字段都是它自己的契约。把这些放进平台内核会让内核被单一系统绑架。适配桥是一个独立脚本，通过 Bridge 协议与平台耦合。备选：在平台里内置各系统适配（内核膨胀）。

### D4 适配桥用后端自带的工具审计作为轨迹来源

后端已经把每次工具调用写进自己的审计表并对外暴露。适配桥读取该审计并转换成 Bridge 的工具调用字段，避免要求后端改代码。这也让「平台不重复执行工具」这一约束自然成立。

## Risks / Trade-offs

- [上下文变量在异步或多线程下可能串用例] → 运行器在单个用例的执行窗口内设置与重置；Bridge 的调用是同步的，当前实现安全。异步调度不在本能力范围。
- [适配桥依赖后端的会话与审计契约，后端改字段会失效] → 失效时表现为该用例判 error 并带出后端错误，不会被误判为通过。
- [真实后端的启动与重置很慢，逐用例重置会显著拉长整轮时间] → 沙箱的命令超时可显式配置；建议把重资源场景与轻场景分成不同的任务集。
