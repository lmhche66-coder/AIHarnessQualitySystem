# Proposal

## Why

端到端任务目前只跑一次。对确定性流程够用，但真实 agent 会波动：同一条任务可能第一次没做成、第二次做成了。只跑一次的通过率把这种波动当成失败，既低估了能力，也看不出稳定性。业务方真正要问的是「跑三次能成几次」。

## What Changes

- 任务可以声明尝试次数；每次尝试从全新的环境与全新的 agent 开始。
- 每次尝试产出独立的判定结果，标识包含尝试序号，因此门禁能按尝试维度设置阈值。
- 报告任务在 k 次尝试内至少解决一次的比例，以及首次尝试即解决的比例。
- 运行元信息包含逐任务的尝试数、成功次数与是否解决。
- 尝试次数为一次时，行为与既有语义完全一致。
- 尝试次数小于一被拒绝，而不是当作一次。
- **BREAKING**：无。既有任务不声明尝试次数时默认一次。

## Capabilities

### New Capabilities

- `repeated-attempts`: 任务的重复尝试执行、逐次判定、pass@k 与 pass@1 统计。

### Modified Capabilities

- `e2e-tasks`: 任务通过率的口径从「单次执行是否解决」扩展为「多次尝试内是否至少解决一次」，并新增首次尝试通过率。

## Impact

- `TaskCase` 新增尝试次数字段，默认一次。
- `TaskRunner` 对每个任务按尝试次数循环，逐次重建环境与 agent。
- `summarize_tasks` 改为按尝试聚合；新增 `summarize_attempts`。
- CLI 的 `task run` 输出增加 pass@k 与 pass@1。
- 新增示例任务与示例波动 agent，用于演示 pass@k 确实能区分「不稳定」与「不行」。
- 依赖无新增。
