# Design

## Context

- 既有 `e2e-tasks` 提供任务定义、干净环境、agent 协议与通过率统计。See proposal.md - Why。
- 任务目前只跑一次，把随机波动当成能力不足，也看不出稳定性。
- 硬约束：重复尝试不得引入跨尝试的状态残留，否则 pass@k 本身就成了噪声。

## Goals / Non-Goals

**Goals:**

- 区分「做不成」与「不稳定」：同时给出 pass@k 与 pass@1。
- 每次尝试完全隔离，环境与 agent 都重建。
- 逐次判定进入既有运行记录与门禁，不新增结果格式。
- 单次尝试的行为与既有语义完全一致。

**Non-Goals:**

- 不做多次运行之间的横向对比与趋势分析。
- 不做统计显著性检验，本变更只给出比例。
- 不做尝试之间的学习或经验传递，每次都是独立尝试。
- 不做成本的重复计数合并，token 与调用指标按尝试累加。

## Decisions

### D1 尝试序号进入判定标识，而不是汇总成一条判定

门禁按判定维度工作。如果把多次尝试压成一条判定，就丢失了「第几次失败」这个信息，也无法按尝试维度设阈值。逐次判定让既有门禁零改动即可覆盖，同时保留稳定性信息。
备选：每任务只产出一条聚合判定（丢失逐次明细，门禁无法区分波动与全败）。

### D2 单次尝试不追加序号

既有的基线、回归比对与回流资产都以判定标识为键。默认尝试一次时保持标识不变，既有基线与候选用例无需重建。
备选：一律追加序号（会导致既有基线与门禁历史全部失配）。

### D3 环境与 agent 都按尝试重建

尝试之间唯一共享的是任务定义。环境按既有工厂重建；agent 同样每次重建，避免 agent 自身记忆把第二次尝试变成「开卷考试」。
备选：agent 只建一次（状态会在尝试之间泄漏，pass@k 失去意义）。

### D4 任务的解决口径是「任一次通过」

这与 pass@k 的标准口径一致：k 次内至少成功一次即算解决。稳定性由首次通过率单独表达。
备选：要求每次都通过（把不稳定的 agent 直接判为失败，无法区分能力与稳定性）。

### D5 尝试次数上限由使用方声明，平台不设默认重复

默认一次，重复是显式选择。否则既有任务会凭空变慢并放大成本。
备选：默认重复三次（既有任务全体变慢，成本翻倍且不易察觉）。

## Risks / Trade-offs

- [重复尝试会成倍放大成本] → 默认一次，重复需显式声明；调用与 token 指标按尝试累加，成本可见。
- [小样本下 pass@k 仍不稳定] → 报告同时给出尝试数，使用者自可判断。
- [逐次判定会让运行记录变大] → 与既有轨迹体积同源，沿用同一套清理策略。
- [波动 agent 的门禁阈值需要调整] → 门禁支持按比例阈值；本变更只提供数据，不替使用方决定阈值。

## Migration Plan

- 新增可选字段，默认一次；既有任务、基线与候选用例行为不变。
- 回滚：移除尝试次数字段与逐次循环，恢复单次执行。
