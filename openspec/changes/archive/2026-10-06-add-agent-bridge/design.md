# Design

## Context

See proposal.md - Why。平台现有接入面全部经过 `load_factory`，只接受 `package.module:factory` 与 `path/to/module.py:factory`，因此被测对象被绑定在「Python 可导入、同进程」。`load` 的 HTTP 压测与 `mcp` 的 stdio 客户端证明平台已经能在两种远程/跨进程形态下工作，但这两条路径各自独立，没有被抽象成通用的 agent 接入。

## Goals / Non-Goals

**Goals:**

- 用一份协议覆盖四类评测能力，agent 只需实现一次。
- 用两种传输覆盖「远端服务」与「本地进程」两类主流形态。
- 让工具执行可以在平台侧或 agent 侧，适配「平台提供工具」与「agent 自带工具」两种现实。
- 用注册表把公司内部多个 agent 管起来，并把结论绑定到版本。

**Non-Goals:**

- 不做分布式调度、队列、GPU 配额与容器编排。
- 不做网关旁路采集与多语言 SDK，只提供协议与两种内置传输。
- 不做多租户、权限与审计。
- 不替换既有 `module:factory` 快路径。

## Decisions

### D1 定义一份 wire 协议，而不是为每个 agent 写适配器

逐个适配无法扩展：公司内部 N 个 agent 会出现 N 套胶水。标准协议把成本从 N 降到 1，agent 只需实现一个入口。备选：为每个 agent 写 Python 适配器（不可持续）。

### D2 两种传输：HTTP 与子进程

HTTP 覆盖远端服务、容器与其他语言；子进程覆盖本地命令行 agent，且无需网络。两者共用同一份协议，只是载体不同。备选：只做 HTTP（本地 agent 要额外起服务）或只做子进程（跨主机不可用）。

### D3 工具执行拆成平台执行与 agent 执行两种模式

生产 agent 往往自带工具，评测环境却希望提供受控工具。两种模式分别对应这两类现实：平台执行让 agent 只做决策、平台负责调用与回传；agent 执行让 agent 保留自主权、平台只记录调用供过程断言。备选：强制一种模式（会排除一半接入方）。

### D4 平台驱动多步循环，而不是要求 agent 自己循环

在平台执行模式下，上一轮工具结果需要回传给 agent 才能继续。由平台驱动循环，agent 每次只需处理一轮，与既有 `TurnBasedAgent` 的「平台掌握循环」一致，也让步数上限与轨迹记录留在平台侧。备选：要求 agent 内部循环（平台失去控制权，防跑飞困难）。

### D5 注册表用文件而不是数据库

中小公司规模下，一个版本化的注册表文件即可满足多 agent 管理与审计需求，且随代码评审、随仓库分发。备选：引入数据库与服务（对当前规模是过度设计）。

### D6 保留 `module:factory` 作为零成本快路径

既有接法已经工作且有测试覆盖，Bridge 是增量而非替代。CLI 按引用前缀分派：`@` 走注册表、`http(s)://` 与 `cmd:` 直连、其余按工厂加载。

### D7 版本绑定写入运行记录

一次评测必须能回答「测的是哪个应用的哪个版本」。注册表条目自带版本，运行记录记录标识与版本，使结论可追溯；这是中小公司最容易被忽略、又最容易补上的一环。

## Risks / Trade-offs

- [agent 不响应或半途卡住] → 每次调用带超时，超时判 error 并回收子进程。
- [协议版本演进导致不兼容] → 请求与响应都带协议版本，不匹配时显式拒绝而不是猜测。
- [平台执行模式下的循环跑飞] → 设定步数上限，超限判失败并说明循环被截断。
- [本地子进程泄漏] → finally 中终止并回收，异常路径同样保证清理。
- [注册表与服务实际状态漂移] → 提供可用性检查，在评测前暴露不可达而不是等到用例中途失败。
