# Design

## Context

- 既有 `trace-persistence` 提供命名轨迹的保存与引用；`trace-assertions` 提供过程断言；`failure-reflow` 依赖轨迹作为证据。See proposal.md - Why。
- 真实 agent 多数跑在平台之外，工具调用记在自己的审计日志里。kingfar-aiops 是第一个具体例子：它的审计已含工具名、参数、三态生命周期、时间戳与耗时。
- 硬约束：导入不得改变平台自身的判定语义，也不得让缺失的数据看起来像失败的证据。

## Goals / Non-Goals

**Goals:**

- 外部审计能变成可求值的轨迹，且不改动外部 agent 的代码。
- 三态生命周期映射准确，未结束的调用不被编造成结果。
- 源数据缺失导致的不可评估被如实标注。
- 导入的轨迹与自有轨迹地位相同，指标与门禁照常工作。

**Non-Goals:**

- 不做 OTLP 线格式的解析，本变更只覆盖工具调用审计这种结构化导出。
- 不做基于 LLM 的字段推断，只做确定性映射。
- 不做审计数据的脱敏，源头已按自身策略处理，界面上也不提供原始敏感参数。
- 不做多来源合并与去重。

## Decisions

### D1 导入契约以「工具调用审计」为中心，而不是以某个框架为中心

审计记录的字段集合（工具名、参数、状态、起止时间、耗时、结果摘要、错误消息）是跨框架都成立的观察面。以它为中心，接入方只需导出这些字段，不绑定任何 agent 框架。
备选：为 LangGraph、OpenAI、MCP 各写一套适配（每多一个框架就多一份维护债）。

### D2 三态生命周期映射为成功、失败、未结束

审计里存在「只有 started、没有终态」的记录，这代表调用被中断。把它当作失败是编造，把它当作成功更危险；保留为未结束才能如实反映。
备选：中断记为失败（丢失与真实失败的区别）；中断丢弃（静默减少步骤，影响序列与调用次数判据）。

### D3 区分「值记录为空」与「值未被记录」

自有轨迹总会写入返回值字段（可能为空），而审计只提供有界摘要。若把两者混为一谈，状态传递判据会报「状态丢失」，而真实原因是源数据里没有值。区分之后判据能给出正确归因。
备选：把结果摘要塞进返回值字段（摘要与真实值不同，会让状态传递判据产生假失败）。

### D4 缺失必需字段直接拒绝，不跳过

跳过坏记录会得到一个步骤变少的轨迹，而步骤数量本身是判据的输入，静默跳过会污染结论。拒绝并指出位置，才能让使用者修数据。
备选：跳过并警告（轨迹与真实执行不一致，且警告容易被忽略）。

### D5 耗时由导入的时间戳推导，不额外引入字段

平台已经用轨迹首尾事件计算耗时。导入时把完成时间作为事件时间，跨度即近似总耗时，无需新增指标通道。
备选：单独维护导入耗时字段（与既有指标口径分叉）。

## Risks / Trade-offs

- [结果摘要无法替代原始返回值] → 已在保真度报告中标注，不假装可评估。
- [审计时间戳精度或时钟漂移影响耗时指标] → 耗时口径本身就写明是事件跨度近似，不宣称精确。
- [CSV 中的 JSON 参数列可能被转义] → 解析按标准 CSV 引号规则处理，并用真实导出格式的样例做验证。
- [不同系统的状态取值不同] → 契约要求接入方把状态归一到完成/失败/未结束三类，映射规则写进规格。

## Migration Plan

- 新增模块与命令，既有事件写法与判据行为不变；状态传递判据仅在「值未记录」时改变归因文字，结论仍为失败。
- 回滚：移除导入模块与子命令，删除「值是否记录」标记即可。
