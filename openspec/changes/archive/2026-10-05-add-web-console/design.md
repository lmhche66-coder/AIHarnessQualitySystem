# Design

## Context

- 既有各层都把结果写进同一份运行记录：`summary.json`、`verdicts.jsonl`、`traces.jsonl`。See proposal.md - Why。
- 平台产出已经不少，但查看面停在终端输出，团队难以据此讨论与定位。
- 硬约束：控制台必须零依赖、离线可用、只读，且不引入前端构建链——否则它会成为整个仓库里最难维护的部分。

## Goals / Non-Goals

**Goals:**

- 一个命令打开，立刻看到所有运行与明细。
- 只读，绝不触碰既有产物。
- 无外部 CDN、无构建步骤、无新增依赖。
- 后续模块只要产出运行记录，就自动被展示。

**Non-Goals:**

- 不做权限与多用户，控制台默认只绑回环地址。
- 不做在线编辑、重跑与删除。
- 不做实时推送与长连接，页面按需重新拉取。
- 不做图表库级的可视化，指标以数字与简单条形表达。

## Decisions

### D1 服务端用标准库 http.server，前端用原生 HTML/CSS/JS

控制台的价值在于让人看见数据，不在于前端工程规模。引入构建链意味着 node_modules、打包配置与版本漂移，而它只是仓库里的一块展示面。标准库加原生脚本可以做到零依赖、离线可用、打开即用。
备选：引入前端框架与构建步骤（新增依赖与维护面，与「只读展示」的收益不成比例）。

### D2 只读，且默认绑定回环地址

控制台会暴露运行记录里的参数与结果，其中可能含敏感内容。默认只绑 `127.0.0.1`，并且只提供读取接口，可以把这个风险压到最低。
备选：默认绑定全部网卡（一次疏忽就把内部数据暴露到局域网）。

### D3 直接读取既有产物，不新建索引

运行记录已经是控制台需要的全部数据。再建一份索引会引入同步问题，而且索引一旦落后于产物，界面就会撒谎。
备选：建立缓存索引（需要失效策略，且容易与真实产物不一致）。

### D4 缺字段时省略区块，而不是填零

不同版本的运行记录字段不一定齐全。填零会让人误以为「真的没有成本」，省略区块则如实表达「这项数据不存在」。这与平台在其它地方的处理一致。
备选：统一填零（把缺失伪装成观测值）。

### D5 前端不做路由，单页加锚点

控制台只有「列表加详情」一个视图层级。引入路由框架没有收益，反而增加失效点。
备选：引入路由（对单一视图层级是过度设计）。

### D6 提供可注入的服务器构造函数

服务端暴露一个「传入存储与端口、返回服务器对象」的构造函数，测试可以在临时端口启动并直接请求接口，无需启动子进程。
备选：只能在命令行启动（测试必须起子进程，慢且不稳）。

## Risks / Trade-offs

- [原生前端缺少组件复用] → 视图层级只有一层，重复量可控；换取的是零构建与零依赖。
- [运行数量增长后列表变长] → 列表按时间倒序并限制返回条数，详情按需加载。
- [大轨迹拖慢页面] → 轨迹按用例按需加载，不在详情接口里一次返回。
- [控制台暴露敏感参数] → 默认回环绑定；审计导入与脱敏策略仍由各模块自身负责。

## Migration Plan

- 全新命令与静态资源，不影响既有行为。
- 回滚：移除子命令与子包即可。
