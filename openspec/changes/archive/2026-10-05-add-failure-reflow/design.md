# Design

## Context

- 既有 `trace-persistence` 提供命名轨迹的保存与运行级引用；`trace-assertions` 提供过程断言；`quality-gate` 消费运行记录。See proposal.md - Why。
- 平台能产出失败判定，但失败之后没有下一步，真实失败样本无法变成可反复执行的资产。
- 硬约束：从一条失败轨迹里不能推断出「应该怎样」。把「agent 做过的」当成「agent 应该做的」，会产出一条永远通过的假用例。

## Goals / Non-Goals

**Goals:**

- 失败可归因：哪条用例、哪条判据、期望与实际分别是什么。
- 可复现的失败被转成能脱离 agent 独立重跑的回归用例。
- 不可复现的失败被如实标记，不产出假通过用例。
- 候选用例在交付前自证能复现原失败。

**Non-Goals:**

- 不做 LLM 归因与根因分析，只做结构化的确定性归因。
- 不自动修改或新增期望值；期望一律沿用原用例，不凭空生成。
- 不从环境状态类失败生成候选用例。
- 不做失败样本的去重、聚类与生命周期管理。

## Decisions

### D1 期望一律沿用原用例，绝不从失败轨迹反推

失败轨迹记录的是「agent 做了什么」，不是「agent 该做什么」。从它反推期望会产出一条必然通过的用例，看起来闭环了，实际什么也没守住。因此候选用例只搬运原用例已有的判据。
备选：用失败轨迹反向生成期望（产出永远通过的假用例，比不做更糟）。

### D2 只保留依赖轨迹的判据

终态判据依赖环境，轨迹里没有它需要的信息。把终态判据一起搬进候选用例，会让候选用例在轨迹求值路径上无法评估。因此候选用例只保留轨迹相关判据，并在报告里说明被丢弃的部分。
备选：把全部判据搬过去（候选用例不可评估，或直接误判）。

### D3 环境依赖的失败标记为不可自动回流

这类失败需要原始环境才能复现。把它标记出来并说明原因，比生成一条无法复现的用例更有用。
备选：跳过不报（使用者以为所有失败都已回流）。

### D4 候选用例在产出前自证可复现

生成的候选必须对证据轨迹重新求值，并得到与原失败相同的失败判据集合。这是唯一能证明「这条回归用例真的守住了原问题」的检查，也把生成器自身的错误挡在交付之前。
备选：生成即交付（生成器一旦有偏差，入库的都是假用例）。

### D5 用例级轨迹引用优先于运行级

一次失败的证据轨迹各不相同。若只有运行级引用，多条候选用例就无法在同一次运行里各自绑定证据。加上用例级引用后，候选用例集合可以整体重跑。
备选：每条候选单独跑一次（运行记录碎片化，门禁无法整体消费）。

### D6 归因需要原始用例定义

运行记录只保存判定与轨迹，不保存用例定义。因此归因需要用户提供原始用例文件，默认取运行元信息里记录的文件路径，缺失时明确报错。
备选：把用例定义写进运行记录（更自包含，但会让运行记录格式变更，留给后续变更）。

## Risks / Trade-offs

- [候选用例依赖原始用例定义，定义被改动后归因会失真] → 报告中记录来源运行与用例标识，便于对照。
- [只覆盖轨迹相关判据，覆盖面有限] → 明确写在报告里，避免给出「全部失败已回流」的错误印象。
- [证据轨迹包含工具返回值，可能有敏感数据] → 与既有轨迹存储同一问题，边界在文档中说明，不在本变更引入脱敏。
- [未做候选用例去重，反复归因会累积重复用例] → v1 接受，去重与生命周期管理留给后续变更。

## Migration Plan

- 新增字段与新增命令，既有用例与运行格式不变；过程用例的 `trace` 字段可选。
- 回滚：删除 triage 模块与子命令，`ProcessCase.trace` 字段移除即可。
