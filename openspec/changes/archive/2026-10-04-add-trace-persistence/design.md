# Design

## Context

- 既有 `trace-assertions` 提供工具调用归一化与四类过程断言；`record-replay` 提供工具交互的确定性重放；`quality-gate` 消费运行记录做准入判定。See proposal.md - Why。
- 过程用例目前只能由运行器当场驱动步骤。真实 agent 的轨迹既无法落盘，也无法在 CI 里复评。
- 硬约束：对已保存轨迹求值时必须完全不调用工具，否则「复评」会重新引入环境噪音，等于没做。

## Goals / Non-Goals

**Goals:**

- 轨迹成为可命名、可列举、可追溯来源的评测资产。
- 过程用例既能被当场驱动，也能对固定轨迹求值，且两个来源互斥。
- 对固定轨迹求值的运行同样进入运行记录，因此可直接被门禁消费。

**Non-Goals:**

- 不做轨迹的编辑、裁剪与合并。
- 不做跨轨迹的对比与可视化。
- 不做轨迹的自动压缩与生命周期清理。
- 不定义真实 agent 如何调用记录包装器，只提供保存入口与该入口的文档。

## Decisions

### D1 轨迹按命名文件存储，事件逐行写入并配元信息文件

`<name>.jsonl` 存事件，`<name>.meta.json` 存名称、来源用例、事件数与来源运行标识，与既有的 cassette、运行记录、基线保持同一形态。逐行写入便于流式读取与人工排查。
备选：单个 JSON 文件（大轨迹需要整体重写）；数据库（v1 复杂度不必要）。

### D2 对固定轨迹求值时零工具调用

求值路径不接触工具注册表，因此不可能因为环境变化而改变结论。这一点用「工具被调用即抛错」的炸弹注册表来验证，而不是靠约定。
备选：仍构造注册表但约定不调用（约定会在重构中被破坏）。

### D3 两个轨迹来源互斥，冲突显式报错

步骤与外部轨迹同时出现时，无法判断用户想要哪一个。静默选一个会让运行结果难以解释，因此直接判 error 并说明冲突。
备选：外部轨迹优先（用户可能误以为在驱动步骤，得到的结果无法解释）。

### D4 既无步骤也无外部轨迹时显式报错

此前这种用例会驱动零个步骤，然后所有过程断言因「没有调用」而失败。虽然结论也是不通过，但原因指向错误的方向。本变更改为明确的 error，指出缺少轨迹来源。
备选：保持原样（错误信息误导排查方向）。

### D5 判定所依据的轨迹随运行一起落盘

运行记录里保存该次判定实际使用的轨迹，判定可以被复查。代价是同一轨迹被多条用例引用时会在运行记录中重复出现，v1 接受该冗余。
备选：只记名称（运行记录不再自包含，轨迹被覆盖后无法复查）。

### D6 引用不存在的轨迹在写入运行之前失败

运行前先解析轨迹引用，解析失败即以非零退出码结束且不产生运行记录，避免留下一次没有意义的空运行。
备选：写入一次全部 error 的运行（会污染运行列表与基线）。

## Risks / Trade-offs

- [同一条轨迹被多条用例引用时运行记录体积成倍增长] → v1 接受；后续可改为按轨迹标识去重存储。
- [轨迹落盘包含工具返回值，可能含敏感数据] → 记录包装器可在工具层脱敏；本变更不新增脱敏机制，边界在文档中说明。
- [轨迹与产生它的代码版本可能脱节] → 元信息记录来源运行标识与创建时间，便于判断轨迹是否陈旧。
- [没有轨迹清理策略] → 与运行记录、cassette 面临同样的问题，统一留给后续变更。

## Migration Plan

- 既有过程用例（声明步骤）行为不变；只有显式引用外部轨迹时才走新路径。
- 回滚：删除轨迹存储模块与 CLI 子命令，`--trace` 选项移除即可。
