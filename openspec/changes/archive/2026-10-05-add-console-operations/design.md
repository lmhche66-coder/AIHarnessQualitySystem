# Design

## Context

- 既有 `console-actions` 已定义写操作边界与不可破坏既有产物的约束；`judge-calibration`、`trace-import`、`failure-reflow` 与运行器分别提供四项能力的业务逻辑。See proposal.md - Why。
- 这四项的共同点是都需要人参与，而命令行入口把它们挡在了日常工作流之外。
- 硬约束：新增操作不得绕过既有的回环地址边界，也不得破坏既有运行与结论记录。

## Goals / Non-Goals

**Goals:**

- 四项人工密集型操作可以在界面上完成。
- 操作失败时给出可定位的原因，而不是笼统失败。
- 复用既有业务逻辑，不把规则复制到路由层。

**Non-Goals:**

- 不做作业队列与后台执行：四项操作都是本地、短时、同步的。
- 不做压测触发：它有真实破坏力，不适合浏览器一键执行。
- 不做多用户与权限，操作边界仍由回环地址承担。
- 不做富文本与键盘快捷键，标注界面保持最小可用。

## Decisions

### D1 业务逻辑放在独立模块，路由只做校验与序列化

四项操作背后是既有模块的编排。把编排写在 `console/actions.py`，路由层只负责解析请求、调用编排、把结果或错误转成 HTTP 响应。这样同一段逻辑既能被界面调用，也能被将来的命令行复用，规则不会分叉。
备选：把编排直接写在请求处理器里（规则散落在 HTTP 层，测试需要起服务）。

### D2 四项操作全部同步执行

契约、过程与任务运行都是秒级且确定性的，同步执行让界面逻辑最简单：提交后直接得到结果。代价是运行期间请求被占住，因此明确不把压测放进这条路。
备选：引入作业队列（对秒级操作是过度设计，且要额外处理进度、取消与重连）。

### D3 金标集与回流产出的用例落在运行根目录下

`gold/` 与 `cases/` 与既有的 `runs/`、`reports/`、`baselines/` 平级，职责清晰，且都随 `--home` 一起切换，便于按环境隔离。
备选：写在仓库里的固定路径（多环境会互相覆盖）。

### D4 上传内容由浏览器读取后以 JSON 提交，服务端不接受任意文件路径

轨迹上传与金标集创建都走「浏览器读文件、以文本提交」。这样服务端不需要按用户给的路径读任意文件，边界更清晰，也避免把本地文件系统暴露成一个读取接口。
备选：接受文件路径由服务端读取（等于开放任意文件读取）。

### D5 运行触发与命令行同属一个信任边界

注册表是用户提供的 Python 工厂，从界面触发意味着浏览器可以间接执行它。这与命令行 `--registry` 是同一件事，不是新引入的风险，因此沿用同一条边界：只在回环地址下允许。
备选：为界面单独设计一套受限注册表格式（需要新协议，且与既有的工具接入方式分叉）。

### D6 运行失败不当作请求失败

触发的运行里存在失败用例，说明评测跑通了并发现质量问题，不是请求出错。只有「跑不起来」（文件缺失、注册表载入失败）才算请求错误。
备选：把失败用例也返回 4xx（把评测结论与调用错误混为一谈）。

### D7 四项操作共用一套错误语义

缺少输入返回 400、目标不存在返回 404、内容不合法返回 400，且响应体带可读原因。统一的错误语义让前端可以按状态码分支，不需要为每个操作写一遍解析。
备选：每个操作自定义状态码（前端分支爆炸）。

## Risks / Trade-offs

- [同步运行会占住请求] → 明确只支持秒级操作；压测与长任务不在此列。
- [界面触发运行会执行用户代码] → 与命令行同一信任边界，且受回环地址限制；文档中写明。
- [标注结果显示的是金标集内容] → 金标集可能存在真实业务文本，因此仍受回环边界保护。
- [上传大文件会占用内存] → 请求体大小上限由服务端显式限制，超限直接拒绝。

## Migration Plan

- 新增模块、目录与视图，既有视图与接口不变。
- 回滚：移除新增路由与视图，删除 `actions.py` 与两个目录即可。
