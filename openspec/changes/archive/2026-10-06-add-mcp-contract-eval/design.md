# Design

## Context

See proposal.md - Why。既有 L1 契约层通过 `Tool` 协议直接调用进程内的 Python 工具（见 `agenteval.contracts`），观察对象是 `ToolResult`。MCP server 是另一类被测对象：它在独立进程里，通过 JSON-RPC 暴露能力，平台必须先完成协议会话才能拿到工具清单与调用入口。函数选择打分则既不属于工具也不属于 server，它是「agent 选了哪个工具」这件事的独立评分。

## Goals / Non-Goals

**Goals:**

- 用手写的最小 MCP 客户端跑通真实 stdio 会话，覆盖握手、能力协商与工具调用。
- 把「schema 声明」与「实际拒绝行为」的一致性变成可断言对象。
- 让函数选择打分可解释、可复现，且不需要 LLM。
- 结果落入既有运行记录，门禁与结论层零改动。

**Non-Goals:**

- 不实现 HTTP / SSE / streamable-HTTP 传输，只做 stdio。
- 不覆盖 MCP 的 resources、prompts、sampling、elicitation 能力。
- 不解析 agent 的自然语言输出；实际调用列表由接入方给出。
- 不做工具返回内容的语义评判，那属于裁判层。

## Decisions

### D1 自建最小 MCP 客户端，而不是依赖官方 SDK

官方 SDK 会带来新依赖、版本漂移与网络安装需求，而平台其余部分刻意保持零外部服务依赖。stdio 会话只需要 JSON-RPC 2.0 的请求/响应/通知三种消息形态，自建客户端约两百行即可覆盖本能力所需子集，且行为完全确定。
备选：接入 `mcp` SDK（依赖重、对协议版本敏感、离线受限）。

### D2 用真实子进程，而不是 mock 传输

「平台能不能跟真实 MCP server 说上话」正是要验证的东西。mock 传输只能验证平台自己的解析代码。因此用例直接声明 server 命令与参数，平台拉起子进程并通过管道收发消息。
备选：伪造一个内存传输（无法发现握手与进程生命周期问题）。

### D3 协议错误与工具错误分层

JSON-RPC 层错误（方法不存在、协议不符）与工具执行错误（`result.isError`）是两类不同失败。参数校验失败在 MCP 语义里属于后者，因此断言期望的是结构化错误信号，二者任一出现都算「被拒绝」，但消息里区分来源，避免把协议故障误判成契约通过。

### D4 schema 与行为一致性作为独立断言

「清单里声明了必填参数」与「缺失时真的拒绝」是两件事，很多 server 只做到其一。专门的一致性断言会主动构造一个缺失必填的调用，观察实际行为，从而暴露「schema 只是装饰」的实现。

### D5 选择打分用调用集合比对，而不是文本相似度

文本相似度既不可解释也不稳定。选择打分把调用规整为「函数名 → 参数」的集合，逐项比对并输出具体差异（错选/漏选/多选、参数名与值的差异），结论可复现、可定位。

### D6 拆成两个 capability

MCP 契约的被测对象是 server，选择打分的被测对象是 agent 的选择行为，两者的输入、生命周期与失败语义都不同。拆成 `mcp-contract-eval` 与 `tool-selection-scoring` 两个 capability，避免把「外部协议验证」与「内部选择评分」耦合成一个笼统的大能力。

## Risks / Trade-offs

- [server 不响应会让运行挂起] → 每次会话与每次调用都带超时，超时按 error 处理并终止子进程。
- [要求 stdin 按行分隔 JSON，非标 server 会失配] → 明确约定行分隔的 JSON-RPC；不满足时给出可读错误而不是静默卡死。
- [子进程可能泄漏] → 在 finally 中终止并回收进程，异常路径同样保证清理。
- [只覆盖 stdio 传输] → 远程 MCP server 需要先落到本地可由 stdio 启动的形态；HTTP 传输列入非目标。
- [选择打分依赖接入方提供结构化调用列表] → 这是刻意的：解析自由文本属于接入方或裁判层，打分本身只应处理已结构化的调用。

## Migration Plan

- 新增两个模块、两类用例与两个 CLI 子命令，既有用例类型与协议不变。
- 回滚：移除新增模块与命令，既有各层不受影响。
