# Design

## Context

- 前七层都在验证 agent 的产出质量；`console` 提供展示面；`quality-gate` 消费运行记录。See proposal.md - Why。
- UI 可交付性与 agent 质量解耦：接口全绿不代表按钮能点、文案不溢出。
- 硬约束：真实浏览器依赖体积大且需要下载浏览器二进制，因此它必须是可选依赖，不能让默认安装变重。

## Goals / Non-Goals

**Goals:**

- 用声明式流程描述用户路径，非工程师也能读懂。
- 流程与驱动解耦，先在脚本驱动上验证引擎，再用真实浏览器跑。
- 失败留下截图——没有截图的 UI 失败无法定位。
- 结果并进统一运行记录。

**Non-Goals:**

- 不做移动端驱动（Appium 或 Maestro）：本变更只覆盖 Web，移动端留给接入方按同一驱动协议扩展。
- 不做视觉回归与像素比对。
- 不做录制回放式的流程生成，流程由人声明。
- 不做驱动池与并发执行，流程串行执行。

## Decisions

### D1 流程与驱动解耦，先用脚本驱动验证引擎

真实浏览器又慢又重，不适合验证「断言引擎本身是否正确」。把驱动抽象成协议，脚本驱动负责在单元测试里精确模拟各类页面状态，真实驱动负责端到端确认。两层各自可测。
备选：只做浏览器驱动（引擎逻辑的测试要么慢要么不覆盖）。

### D2 Playwright 作为可选依赖，缺失时给出明确原因

浏览器驱动加二进制体积可观，把它放进默认依赖会让「只想跑契约测试」的人付出不必要的安装代价。缺失时驱动抛出的错误要说清需要装什么。
备选：放进默认依赖（安装变重）；完全不提供实现（使用方要自己写）。

### D3 只在失败时截图

截图是定位失败的证据，不是每次都需要的产物。只在未通过时保存，避免产物随运行次数线性增长。
备选：每步都截（产物爆炸，且绝大多数没人看）。

### D4 步骤异常与断言不满足分开

步骤抛异常说明流程跑不完（选择器错、页面没加载），断言不满足说明页面状态不对。两者的排查方向不同，因此分别记为 error 与 fail。
备选：都记为失败（无法区分是脚本写错还是页面不对）。

### D5 预算只做步骤数与总时长

UI 的性能指标（首屏、可交互时间）属于另一类问题，浏览器已经能测；这里只防「流程无限等待」与「流程越写越长」这两件容易失控的事。
备选：把性能指标也塞进来（与既有压测层重叠）。

## Risks / Trade-offs

- [真实浏览器在 CI 里需要额外安装] → 默认测试用脚本驱动；浏览器驱动的测试在未安装时跳过，不阻塞流水线。
- [选择器脆弱，页面一改流程就红] → 这是 UI 测试的固有成本，流程数量应保持精简，优先覆盖关键路径。
- [截图产物体积] → 只在失败时产生，并随运行记录一起清理。
- [不覆盖移动端] → 明确写为非目标；驱动协议留出了接入空间。

## Migration Plan

- 新增模块、命令与可选依赖，既有行为不变。
- 回滚：移除模块与子命令即可，可选依赖不影响默认安装。
