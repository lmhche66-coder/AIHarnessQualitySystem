# Design

## Context

- 仓库当前除 OpenSpec 脚手架外为空，无既有代码约束，因此本设计只解决第一层（工具调用契约）如何落成可运行的代码。
- See proposal.md - Why 了解动机，本文件不重复。
- 运行环境为 Python 3.10，本机已可用 `pydantic` 2.x、`jsonschema`、`pyyaml`；`pytest` 需要安装。
- 关键约束：这一层不调用 LLM、不依赖真实外部服务，因此同一用例重复执行必须得到相同结论。

## Goals / Non-Goals

**Goals:**

- 建立可被后续层复用的最小数据模型：Case / Trace / Verdict / Run。
- 让六类契约缺陷可声明、可执行、可复现。
- 运行结果可落盘、可回读，并可由 CLI 与后续门禁消费。
- 以 pytest 作为主断言载体与运行入口，避免自研 runner。
- 提供故障注入桩件，使超时、限流、部分失败无需真实服务即可稳定触发。

**Non-Goals:**

- 轨迹级断言、LLM 裁判、端到端沙箱、CI 门禁、可观测后端、性能压测与安全红队，均为后续变更。
- 不实现通用插件系统，工具通过显式注册表接入。
- 不做图形化界面。

## Decisions

### D1 数据模型使用 pydantic v2

契约层本身就是 schema 校验层，pydantic 提供字段校验、序列化与可定位的错误信息，并与 `jsonschema` 生态可互转。
备选：`dataclasses` 加手写校验（错误信息质量差，重复劳动）；裸 `jsonschema` 字典（无类型提示，IDE 支持弱）。

### D2 用例以 pydantic 模型为唯一真源，Python 与 JSON/YAML 均为其输入形式

需要同时满足两种诉求：开发者在 pytest 里直接写用例，以及后续从线上 trace 回流生成用例。以模型为真源可以两者兼得。
备选：纯 YAML 声明（复杂场景表达力不足）；纯 Python（无法从结构化数据回流）。

### D3 契约断言的对象是「可观测结果」，不是平台自身的校验逻辑

断言检查工具返回的是结构化错误、成功结果还是未处理异常，因此既能验证用户自带工具，也能验证平台提供的基类。平台另提供带 schema 校验的工具基类，让用户默认获得合规行为，但断言不依赖该基类。
备选：由平台统一在调用前做参数校验（会导致契约测试只验证平台，无法发现用户工具的真实缺陷）。

### D4 运行结果采用「每运行一个目录」的 JSONL 加 summary.json

JSONL 可追加、可流式读取，便于后续把失败样本回流成新用例；summary.json 便于 CLI 快速展示与门禁读取。
备选：SQLite（v1 引入不必要复杂度，后续可加）；单一 JSON 大文件（大运行需全量重写）。

### D5 运行目录默认 `.agenteval/runs/`，可由环境变量覆盖

默认值与源码分离，避免污染工作区；通过 `AGENTEVAL_HOME` 覆盖可支持 CI 与多环境隔离。
备选：写入系统临时目录（结果不可回读，违背持久化要求）。

### D6 timeout 用线程执行器实现，保持同步 API

v1 不引入 event loop，`concurrent.futures` 足以隔离超时场景。
已知限制：线程无法强制中断阻塞中的原生调用，该限制会写入文档与错误信息。
备选：`asyncio`（引入同步/异步双栈与额外依赖，对契约测试收益不足）。

## Risks / Trade-offs

- [线程超时无法强杀阻塞调用] → 在文档与错误信息中明确该限制，并要求被测工具提供可中断实现。
- [故障桩件可能掩盖真实工具的语义差异] → 桩件只用于平台自测与演示；契约用例要求用户工具复用同一套断言语义。
- [pydantic 版本升级可能改变错误文本] → 断言错误类型与字段路径，不断言完整错误文本。
- [JSONL 结果随运行次数增长] → v1 接受；后续变更引入清理与索引。
- [超时用例可能因机器负载波动而间歇失败] → 用例声明阈值并要求正负样本；超时判定使用单侧、留出余量的比较。

## Migration Plan

- 仓库为空，无迁移步骤。
- 新增包、测试与运行目录均不影响既有内容。
- 回滚策略：删除 `src/agenteval`、`tests`、`examples`、`pyproject.toml`、`README.md` 即可回到初始状态；OpenSpec 变更目录可整体删除。
