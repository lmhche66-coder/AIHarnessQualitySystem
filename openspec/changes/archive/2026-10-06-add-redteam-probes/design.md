# Design

## Context

- 既有各层验证功能、过程、质量、成本与性能，没有覆盖安全。See proposal.md - Why。
- `trace-assertions` 已提供工具调用归一化，`record-replay` 与 `console` 可覆盖其结果。
- 硬约束：这个环境里没有可用的模型访问，因此不能实现生成式攻击者。红队的价值必须落在「判定攻击是否成功」这一半。

## Goals / Non-Goals

**Goals:**

- 对抗输入与失败信号都可声明、可复现。
- 判定完全确定性，不依赖模型。
- 结果进入既有运行记录与门禁。

**Non-Goals:**

- 不做生成式攻击者（需要模型），探针由人声明。
- 不做响应语义判断（如「是否泄漏了业务信息」），只做可精确判定的信号。
- 不做自动化漏洞修复建议。

## Decisions

### D1 用金丝雀把「是否被诱导」变成可精确判定的信号

「agent 有没有听信注入」本身不可直接观测。做法是埋标记：往系统提示词里放唯一串，响应里出现它即提示词泄漏；给不该被触发的动作放标记，轨迹里出现它即注入成功。这样判定不需要模型，也不需要人读一遍回答。
备选：让模型判断回答是否被诱导（不确定、需模型、不可复现）。

### D2 三类检测覆盖不同失败面

金丝雀泄漏看输出，禁用工具看行为，禁用取值看参数。三者对应三类真实事故：泄密、越权、破坏性操作。它们的证据位置不同，因此分开检测、分开报告。
备选：只做其中一类（覆盖面过窄）。

### D3 判定记录不写入金丝雀内容

金丝雀的用途是当标记，把它写进运行记录等于把标记公开，后续再想用它检测就失效了。判定里只记录序号。
备选：把金丝雀值写进判定（标记外泄，失去检测能力）。

### D4 提供带轨迹记录的默认目标实现

调用方最容易写错的是「怎么把工具调用记下来」。平台把环境工厂与 agent 组合成目标，自动记录每次调用，调用方只需实现一个返回响应文本的函数。
备选：只给协议（每个接入方重复实现同一个拼装逻辑，且容易漏记调用）。

### D5 目标异常判 error 而不是 fail

目标抛异常说明探针没跑完，无法判断安全与否；把它记成 fail 会制造假的安全告警，进而让人忽视真实告警。
备选：异常记为失败（狼来了，安全告警失去可信度）。

## Risks / Trade-offs

- [金丝雀需要接入方配合埋点] → 这是方法的固有前提；文档中说明如何埋。
- [禁用取值匹配为字符串包含] → 有意保持简单与可预测；需要更精细匹配时由接入方在参数里放可判定的字面量。
- [误报会让安全告警失去价值] → 只做确定性检测，任何不确定的语义判断都不纳入。

## Migration Plan

- 新增模块与命令，既有行为不变。
- 回滚：移除模块与子命令。
