# Design

## Context

- `eval-core` 的运行记录与 `trace-assertions` 的轨迹事件已经包含导出所需的全部信息。See proposal.md - Why。
- 上一轮把这块列为未完成，理由是「无法对着真实后端验证，只验证结构价值有限」。
- 本变更用最小 OTLP/HTTP 接收端在测试里真正接一次，因此该理由不再成立。

## Goals / Non-Goals

**Goals:**

- 轨迹能被标准 trace 后端接收，字段符合语义约定。
- 标识确定，重复导出可去重。
- 推送失败可诊断。
- 导出只读。

**Non-Goals:**

- 不实现 gRPC 传输，只做 OTLP/HTTP JSON。
- 不实现批量与重试队列，一次运行一次推送。
- 不导出日志与指标，只导出轨迹。
- 不内置任何后端 SDK，端点由使用方提供。

## Decisions

### D1 只做 OTLP/HTTP JSON，不做 gRPC

OTLP/HTTP JSON 用标准库即可实现，零依赖、可读、便于测试；gRPC 需要 protobuf 与传输库，体积与复杂度都不成比例。主流后端都接受 HTTP 端点。
备选：gRPC（新增依赖）；自研后端 SDK（绑定单一厂商）。

### D2 标识确定性生成

用运行标识、用例标识与序号做哈希派生 trace 与 span 标识。同一份运行重复导出得到相同标识，后端可以据此去重，也让导出结果可被比对。
备选：随机标识（重复导出会产生重复数据，无法去重）。

### D3 语义约定优先，自有字段加前缀

工具调用、token 用量这些有约定名的字段一律用约定名，其余平台自有字段放 `agenteval.*`。这样后端能按标准字段做通用分析，同时不污染保留命名空间。
备选：全部用自有命名（后端无法识别）；全部塞进约定名（占用保留名）。

### D4 三层 span：运行、用例、工具调用

三层结构能同时表达「这次运行整体如何」「哪条用例失败」「失败前调用了什么」。再细分到步骤会让 span 数量爆炸且与既有数据模型不对应。
备选：只导工具调用（丢失用例与运行的上下文）；按轨迹事件逐个导（噪音大）。

### D5 导出失败即命令失败，但不影响本地产物

推送是显式请求的动作，失败必须让人知道，因此退出码非零并打印端点与原因。导出过程只读，任何失败都不会动本地文件。
备选：失败只警告（在 CI 里会被忽略）。

## Risks / Trade-offs

- [语义约定仍在演进] → 只使用稳定且明确的一小部分字段，其余放自有命名空间。
- [大运行的 payload 体积] → 一次运行一次推送；轨迹很长的运行由使用方控制导出范围。
- [端点不可达时命令失败] → 这是期望行为；失败信息包含端点便于排查。
- [不做重试] → 明确为非目标；需要可靠性时由调用方的编排层负责。

## Migration Plan

- 新增模块与命令，既有行为不变。
- 回滚：移除模块与子命令。
