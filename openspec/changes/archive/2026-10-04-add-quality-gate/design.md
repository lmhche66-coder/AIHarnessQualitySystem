# Design

## Context

- 既有 `eval-core` 提供 Run 与 Verdict 及 JSONL 运行存储；`record-replay` 提供确定性回放，使门禁可以在无外部依赖的环境里稳定执行。See proposal.md - Why。
- 当前平台能产出运行记录，但没有任何机制依据记录拦住退化提交。
- 硬约束：门禁要能被 CI 直接消费，结论必须通过退出码表达，报告必须可被机器解析。

## Goals / Non-Goals

**Goals:**

- 基线、阈值、回归三者分离，各自可单独解释。
- 结论用退出码表达，可直接作为 CI 步骤成败。
- 报告同时服务人和机器。
- CI 工作流一次跑通「测试 → 录制 → 回放 → 门禁」。

**Non-Goals:**

- 不做统计显著性检验与置信区间，本变更只做确定性的阈值与回归判定。
- 不做跨多次运行的趋势分析与历史曲线。
- 不做自动回滚或自动发布动作，门禁只负责判定。
- 不做 LLM 裁判分与轨迹级断言，那些属于后续层。

## Decisions

### D1 基线存为用例状态快照，而不是引用某次运行

基线只需要 `case_id → status` 的映射加上来源运行标识。快照体积小、语义清晰，且运行记录被清理后基线仍然可用。
备选：只引用运行标识（历史运行一被清理基线即失效）；存整份 Run（冗余且与运行格式强耦合）。

### D2 阈值与回归分开，二者都能独立让门禁不通过

阈值回答「这次的绝对水平够不够」，回归回答「这次比上次差了没有」。合并成单一分数会丢掉这个区别，报告里也说不清哪里不合格。
备选：只做回归（首次运行无基线时失效）；只做阈值（无法发现「本来就差、又更差了」）。

### D3 基线中存在但当前缺失的用例也算回归

用例凭空消失通常意味着测试或能力被误删，比单个用例失败更值得警惕。计入回归可以防住「静默缩小测试集」这种最容易被忽略的退化。
备选：只比对两边都存在的用例（会漏掉整段能力被删除的情况）。

### D4 无基线时只按阈值判定，并在报告中明确标注

首次接入时还没有基线，此时直接失败会阻塞采用。明确标注「未使用基线」，使用者才知道本次结论的覆盖范围。
备选：无基线即失败（首次接入体验差，容易促使团队绕过门禁）。

### D5 回归豁免是显式开关，豁免后仍要列出

允许回归与静默忽略是两件事。豁免后报告仍逐条列出回归与缺失，保留可见性。
备选：豁免后不输出（会让人误以为没有回归）。

### D6 门禁复用既有运行存储，不引入新的运行格式

门禁只读取 `RunStore` 已落盘的记录，不新增运行侧格式，因此对既有用例与运行器零影响。
备选：门禁自行执行用例（与运行器职责重叠，且无法对历史运行做判定）。

### D7 CI 工作流以门禁命令收尾

工作流串起 pytest、录制、回放与门禁四步，最后一步的退出码即整个 job 的结论，无需额外解析脚本。本地与 CI 执行的是同一组命令，避免两边漂移。
备选：把判定逻辑写进 shell（与本地命令不一致，长期必然分叉）。

## Risks / Trade-offs

- [通过率阈值可能被 flaky 用例误报] → 回放模式本身是确定性的，flaky 主要来自尚未回放的用例；两者配合缓解。
- [基线未随用例集更新而刷新，导致长期失真] → 报告始终显示基线来源运行标识与捕获时间，便于判断基线是否陈旧。
- [只做确定性判定，覆盖不到质量类指标] → 已在非目标中写明，后续由裁判层补充。
- [CI 中录制步骤依赖真实工具可用] → 工作流用内置 demo 注册表，不依赖外部服务；接入真实工具时可改为提交已录制 cassette 只跑回放。

## Migration Plan

- 全新能力，无迁移。既有命令与运行格式不变。
- 回滚：删除 gate 模块、CLI 子命令与工作流文件即可。
