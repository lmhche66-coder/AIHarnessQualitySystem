# Design

## Context

See proposal.md - Why。`console-actions` 当初把副作用搬进浏览器是为了降低门槛，但评测的实际执行者一直是 CLI 与 CI：`gate`、`judge calibrate`、`triage`、`reflow` 都有退出码，会被流水线消费。UI 侧的写入口既不能被流水线使用，又扩大了误操作面。

## Goals / Non-Goals

**Goals:**

- 界面只做「把已有产物看清楚」。
- 分区收敛到四类，读与写的边界在视觉上一目了然。
- 保持后端写接口不变，避免影响既有 API 使用方。

**Non-Goals:**

- 不删除后端写接口，也不改它们的授权边界。
- 不引入权限、登录与多用户。
- 不重做视觉风格，只调整信息架构。

## Decisions

### D1 只改界面暴露面，不动后端接口

后端写接口有独立测试覆盖，且可能被脚本直接调用。删掉它们会扩大变更半径，而问题本身出在界面把两件事混在一起。备选：连同接口一起删（破坏 API 使用方）。

### D2 四分区按「产物类型」划分，而不是按功能

运行、结论、基线、资产各自对应一类落盘产物，读者按「我要看什么」找入口，而不是按「我要做什么」。资产把金标集、轨迹与回流数据集放在一起，因为它们是同一类东西：被复用的评测资产。备选：保留六个按流程命名的分区（读者要先理解流程）。

### D3 资产用纵向区块而不是嵌套标签页

嵌套标签页会让人在两层导航里迷路。三个只读清单上下排列，滚动即可看全，层级只有一层。备选：资产内再开标签页（多一层导航成本）。

### D4 新增只读的回流端点

`reflow` 的产出此前只在文件系统里，界面上看不到。加一个只读端点把它暴露出来，是本次唯一的功能性增量，且与「只保留可视化」的方向一致。

## Risks / Trade-offs

- [有人依赖界面点按完成基线捕获或门禁判定] → 迁移路径写进了 REMOVED 要求里，命令与之前一一对应。
- [只读界面让人觉得能力变少] → 能力没有减少，只是执行者从浏览器换回 CLI 与 CI，这也是它们本来就该在的地方。
