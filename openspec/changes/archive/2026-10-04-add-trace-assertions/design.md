# Design

## Context

- 既有 `eval-core` 提供 Case / Trace / Verdict / Run 与确定性断言；`record-replay` 让工具交互可以被确定性重放；`quality-gate` 消费运行记录做准入判定。See proposal.md - Why。
- 现有断言只覆盖单次工具调用的契约（参数、超时、限流、幂等、回滚），完全不看 agent 的中间过程。
- 硬约束：不引入 LLM 裁判，过程断言必须是确定性的，且结论可重复。

## Goals / Non-Goals

**Goals:**

- 把工具调用归一化成稳定、可检查的序列。
- 覆盖五类过程问题：工具选错、顺序不对、多余步骤、失败未恢复、状态丢失。
- 过程用例与既有运行器、运行存储、门禁无缝组合。

**Non-Goals:**

- 不做 LLM 裁判与语义等价判断，只做确定性结构断言。
- 不做轨迹可视化与跨运行对比。
- 不定义「真实 agent 如何产出轨迹」的完整方案：本变更提供记录包装器与断言引擎，真实轨迹的导入路径留给后续变更。
- 不处理并发调用的顺序语义，v1 按记录顺序线性解释。

## Decisions

### D1 过程用例是独立类型，而不是给工具契约用例加字段

工具契约用例有 `target` 与 `input`，过程用例有 `steps` 与 `checks`，两者必填项不同。用带判别字段的联合类型区分，可以继续用 `extra="forbid"` 精确校验，避免产生一堆「该字段在此类型下无效」的模糊错误。既有 `Case` 模型保持原样，新增 `ProcessCase` 与联合别名。
备选：单一扁平模型加可选字段（校验变松，非法组合需要手写校验）。

### D2 工具调用归一化为独立记录，而不是让断言直接读原始事件

原始轨迹里混有契约检查事件、cassette 命中事件与工具调用事件。断言只依赖归一化后的调用序列，事件命名变化不会波及断言，边界也更清楚。
备选：断言直接遍历 `trace.events`（断言与事件命名强耦合）。

### D3 轨迹中记录工具返回值

状态传递断言需要比较「生产者产出了什么」与「消费者传入了什么」，因此调用记录必须带返回值。代价是轨迹体积增大。
备选：只记录结果状态（无法实现状态传递断言）；只记录摘要（无法比较具体值）。

### D4 顺序断言默认子序列，完全匹配显式声明

真实 agent 常有多余的准备性调用。默认子序列可以守住「关键步骤确实按序发生」，完全匹配留给对步骤数敏感的场景，避免默认过严导致误报后被人绕过。
备选：默认完全匹配（误报多，容易促使团队把断言放宽到无意义）。

### D5 「未观察到失败」判定为失败而不是跳过

恢复断言的目的是证明恢复路径被走过。如果失败从未发生，这条断言没有验证任何东西，判通过会产生虚假的信心。
备选：视为通过或跳过（掩盖恢复逻辑从未被覆盖的事实）。

### D6 过程用例由运行器驱动步骤执行，同时提供独立包装器

过程用例自带 `steps`，运行器按序调用工具并把调用记入轨迹，然后评估断言。这样过程用例无需外部 agent 即可端到端运行与自测；同时提供独立的工具记录包装器，供用户在自己的 agent 里记录真实轨迹。
备选：只接受外部传入轨迹（v1 无法端到端自测）；只提供包装器（用户需自行拼装运行流程）。

### D7 过程断言沿用既有的判定与汇总载体

过程用例产出的是普通 `Verdict`，写进同一个 Run，因此基线、阈值与门禁无需任何改动即可覆盖过程断言。
备选：为过程断言单独建一套结果格式（重复实现汇总、存储与门禁）。

## Risks / Trade-offs

- [记录返回值会放大运行记录体积] → 仅在工具调用事件中记录，可沿用既有运行目录清理策略；后续可加截断与采样。
- [线性顺序解释无法表达并发调用] → 明确写为非目标，并发场景需先确定顺序语义。
- [过程断言可能过拟合某一条实现路径] → 顺序断言默认子序列且允许多余步骤，只有显式选择完全匹配才严格要求步数。
- [真实 agent 的轨迹导入尚未打通] → 本变更先交付记录包装器与断言引擎作为基础，导入路径在后续变更补充。

## Migration Plan

- 既有工具契约用例与运行格式不变；`load_cases` 现在同时接受过程用例。
- 回滚：删除过程模块与新增模型，`load_cases` 恢复为只解析工具契约用例。
