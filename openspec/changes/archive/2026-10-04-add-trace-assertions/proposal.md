# Proposal

## Why

现有断言只看单次工具调用的契约，完全不看 agent 的中间过程。只看最终答案是碰运气的：工具选错但结果凑巧对、顺序颠倒、绕了一圈多余步骤、失败后直接放弃、前一步的状态没有传下去，这些都不会被现有用例发现。成熟项目与玩具项目的分水岭就在这里。

## What Changes

- 新增轨迹级过程断言能力：把工具调用归一化为结构化序列，再对其做确定性断言。
- 新增四类过程断言：工具调用顺序（子序列与完全匹配）、多余调用、失败后恢复、状态传递。
- 新增过程用例类型，声明要执行的工具调用步骤与要验证的过程断言，与其他用例一样产出判定结果。
- 提供工具调用记录包装器，使用户能在自己的 agent 里记录真实轨迹。
- 过程用例结果与其他用例一样进入运行记录，因此可直接被既有门禁消费。
- **BREAKING**：无。既有工具契约用例、运行格式与门禁行为不变。

## Capabilities

### New Capabilities

- `trace-assertions`: 对 agent 执行轨迹做过程级断言，包括工具调用的归一化与记录、顺序断言、多余调用断言、恢复断言、状态传递断言，以及过程用例的执行语义。

### Modified Capabilities

- `eval-core`: 统一数据模型中的评测用例需要区分「工具契约用例」与「过程用例」两类，并各自校验其专属字段。既有四类对象与校验要求不变。

## Impact

- `models.py` 新增 `ProcessStep`、`ProcessCase` 与四类过程检查模型，以及判别联合别名；既有 `Case` 模型保持不变。
- 新增 `agenteval.process` 模块，承载轨迹归一化、记录包装器与过程断言。
- `load_cases` 现在同时接受工具契约用例与过程用例。
- `ContractRunner` 增加对过程用例的分派与步骤执行。
- 依赖无新增，断言逻辑只使用标准库。
- 本变更为后续「导入真实 agent 轨迹」与「端到端任务成功率」打底。
