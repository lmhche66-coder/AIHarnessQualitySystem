# Design

## Context

See proposal.md - Why。`TaskRunner` 目前通过 `EnvironmentFactory` 在每个任务开始时重建一份 `ToolRegistry`，隔离的是进程内对象；真实依赖（数据库、向量库、对象存储）由使用方自行维护，平台既不知道它们的存在，也不管它们的生命周期。仓库里已有真实对象：`kingfar-aiops` 的 `infra/compose.yaml`（compose 项目 `agent-py`），管理 etcd、MinIO、Milvus、PostgreSQL、Redis 等基础设施。

## Goals / Non-Goals

**Goals:**

- 把 compose 项目变成平台可管理的沙箱，具备启停、健康检查、快照与重置。
- 在不改变既有任务协议的前提下，让评测按用例重置环境。
- 让评测结论绑定环境版本，使结果可追溯、可复现。

**Non-Goals:**

- 不做跨主机调度、集群编排与 Kubernetes。
- 不做容器进程级快照（CRIU）与内存态恢复，只做数据卷级快照。
- 不做镜像构建与推送，沙箱使用已存在的镜像。
- 不引入 Python Docker SDK，只调用本机 docker CLI。

## Decisions

### D1 以 compose 项目为沙箱单元，而不是单个容器

真实评测环境通常是一组互相依赖的服务（数据库 + 向量库 + 对象存储）。按容器管理会丢失依赖顺序与网络关系；compose 已经把这份关系声明好了，直接复用它最省事，也与使用方现有资产一致。备选：逐容器管理（要重新表达依赖关系）。

### D2 三种重置策略，而不是一种

`recreate` 最干净但最慢，适合正确性优先的回归；`snapshot` 能回到带预置数据的已知状态，适合需要初始数据的业务任务；`none` 适合只读评测与本地调试。只提供一种会逼使用方在平台外自己写脚本。备选：只做重建（无法表达预置数据）。

### D3 快照走数据卷，而不是数据库导出

数据库导出只覆盖单库，且要为每种服务写一套逻辑。数据卷快照对任何服务都成立，实现统一，代价是需要先停写。备选：逐服务 dump（覆盖面窄、维护成本高）。

### D4 生命周期钩子挂在运行器上，而不是包一层命令

「每个用例前重置」必须发生在用例之间，只能在运行器内部完成；在 CLI 外层包装做不到。因此给 `TaskRunner` 增加可选的沙箱参数，默认不传，行为不变。备选：外层脚本循环调用（无法表达轮内重置）。

### D5 健康门禁前移，失败即整轮失败

环境没起来时继续跑，只会产出一批看起来像模型问题的假失败。因此运行前先做健康检查，不通过就整轮失败，并不产出用例判定。这与 `tasks.md` 里「不制造假安全告警」的既有取舍一致。

### D6 版本绑定用内容哈希，而不是文件路径

路径不能说明内容是否变过。对 compose 文件内容取哈希，并记录镜像标签，才能回答「这次结论对应哪份环境定义」。

## Risks / Trade-offs

- [重建式重置很慢，用例多时整轮耗时会显著上升] → 默认不开启沙箱；开启时建议配合用例筛选或分组重置。
- [卷快照需要先停写，运行中的服务可能写出不一致的数据] → 重置与快照前先停止相关服务，再操作卷。
- [依赖本机 docker，缺少 docker 的环境无法使用] → 沙箱是可选能力，未安装时给出可读错误，不影响其余各层。
- [共享一份 compose 的并发运行会互相干扰] → 明确约束：同一沙箱同一时间只允许一轮运行；并发调度不在本能力范围。
