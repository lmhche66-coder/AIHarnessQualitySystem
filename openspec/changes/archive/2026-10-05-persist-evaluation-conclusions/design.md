# Design

## Context

- 既有各层把判定与指标写进运行记录，`console` 负责展示。See proposal.md - Why。
- 门禁、归因、裁判校准是「消费者」：它们读取已有数据、在终端给结论，不产生新的运行记录，因此既不落盘也不可见。
- 硬约束：结论记录不能变成运行记录的副本，否则两处数据会各自漂移。

## Goals / Non-Goals

**Goals:**

- 三类结论可回看、可检索、可被展示面读取。
- 记录自包含摘要，同时保留完整报告以便追溯细节。
- 与运行记录职责分清：结论引用运行，不复制判定。

**Non-Goals:**

- 不改动既有命令的输出与退出码。
- 不做结论的版本管理、审批流与生命周期清理。
- 不把结论做成一等运行记录，避免门禁对结论再次判定。

## Decisions

### D1 每条结论一个文件，而不是追加进同一个日志

结论之间相互独立，按标识读取是最常见的用法。一文件一记录让读取与删除都变成单文件操作，也便于人工查看。
备选：追加进单一 JSONL（读取需要全量扫描，删除需要重写）。

### D2 结论同时保存摘要与完整报告

展示面只需要摘要，追溯细节需要完整报告。两者都存，避免为了看一个数字而加载整份报告。
备选：只存完整报告（列表视图要加载全部内容）；只存摘要（细节丢失，无法追溯）。

### D3 结论引用运行标识，不复制判定明细

判定明细的唯一来源仍是运行记录。结论里再存一份，会在运行记录被清理或重算后产生两份互相矛盾的真相。
备选：把判定快照进结论（两处数据必然漂移）。

### D4 结论目录与运行目录平级

结论不是运行，放在运行目录里会污染「运行」这个概念，也会让按运行标识检索的代码遇到非运行目录。平级目录职责清晰。
备选：放进运行目录的子目录（运行目录结构被污染）。

### D5 写入失败不改变命令结论

结论落盘是附带的持久化，不应影响判定结果与退出码。写入失败时报告警告，但退出码仍由判定决定。
备选：写入失败即让命令失败（把持久化问题伪装成评测问题）。

## Risks / Trade-offs

- [结论记录会随时间累积] → 与运行记录同一问题，沿用同一套清理策略；本变更不引入新的清理机制。
- [结论引用的运行可能已被删除] → 摘要仍可读，明细不可达；这是引用而非复制的必然代价，已在设计中写明。
- [三类结论结构不同] → 用统一的记录外壳加各自类型的报告体，展示面按类型分支处理。

## Migration Plan

- 新增目录与模块，既有命令输出不变。
- 回滚：删除结论目录与写入调用即可。
