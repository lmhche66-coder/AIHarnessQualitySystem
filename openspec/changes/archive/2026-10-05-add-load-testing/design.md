# Design

## Context

- 既有 `usage-budgets` 已经把调用次数、重复次数、token 与耗时做成一等指标；`quality-gate` 与 `console` 消费运行记录。See proposal.md - Why。
- agent 服务在负载下的失效模式与普通 HTTP 服务不同：成本无上界、流式连接不等于吞吐、瓶颈常在外部模型限额、限流会触发重试形成正反馈。
- 硬约束：不引入压测框架依赖；结论必须与既有指标口径一致，否则控制台与门禁无法统一消费。

## Goals / Non-Goals

**Goals:**

- 用一个命令对 agent 服务施压，得到可解释的结果。
- 延迟看分布不看均值，并单独度量流式首字节。
- 扇出与成本按请求统计，缺失时如实标注。
- 错误按原因分类，便于判断饱和点在哪。
- 结果直接进运行记录，控制台与门禁零改动覆盖。

**Non-Goals:**

- 不做分布式施压与远程执行器，单机线程模型覆盖中小规模验证。
- 不做协议级录制回放，场景以声明式请求模板表达。
- 不做实时曲线与长稳压测的在线监控，本变更只产出一次施压的报告。
- 不做模型侧限额的自动探测，只如实报告限流比例。

## Decisions

### D1 并发用标准库线程，请求用标准库 urllib

压测的瓶颈通常在目标服务与外部模型，而不在施压端。标准库线程模型足以产生有意义的并发，并且零依赖、可离线运行、行为可预测。
备选：引入 asyncio 与 aiohttp（更快，但新增依赖与异步栈，且对「验证服务在并发下是否退化」这个目标收益有限）。

### D2 请求总量与持续时间二者至少其一，而不是只支持总量

总量便于复现与测试，持续时间便于观察稳定性退化。两者都支持，施压以先到者为准。
备选：只支持总量（无法观察随时间的漂移）。

### D3 扇出由响应体按字段路径提取，缺失时标注未观测

平台不知道 agent 服务的响应结构，强行假设字段名会得到静默的零值。让使用方声明字段路径，平台负责提取与汇总；提取不到就标注未观测。
备选：内置假设常见字段名（猜错时静默为零，比没有数据更危险）。

### D4 首字节只在流式场景报告

非流式响应只有一次完整返回，「首字节」等于总耗时，报出来会误导读者以为服务是流式的。按场景显式声明，避免用总耗时冒充响应性指标。
备选：一律报告（非流式下该指标没有独立含义）。

### D5 错误按原因分类而不是只报错误率

错误率的用处有限，因为「谁在报错」决定了下一步该改什么：429 说明撞上外部限额，5xx 说明自身服务不行，超时说明下游卡住。分类是判断饱和点的前提。
备选：只报错误率（无法定位饱和点）。

### D6 未声明预算时照常施压但不判定

压测的常见用法是先摸底再定阈值。没有预算时给出全部指标但不下结论，比默认给一个阈值更有用。
备选：默认套用一组阈值（可能把摸底结果误判为失败）。

### D7 结果同时写入判定与标准指标

压测报告写入运行元信息，标准指标字段（调用数、重复、耗时、token）由报告映射填充，使控制台无需为压测新增代码路径，门禁也按既有语义工作。
备选：为压测另建结果格式（需要给控制台与门禁各加一条分支）。

## Risks / Trade-offs

- [单机线程模型无法产生极大并发] → 明确写为非目标；需要更大规模时应改用分布式施压器，本模块仍可用于验证与回归。
- [响应体提取依赖服务返回用量] → 未返回时标注未观测，不假装有数据。
- [压测会真实消耗模型额度与费用] → 场景需显式声明请求总量与并发；报告给出 token 与成本相关指标，便于评估代价。
- [施压端自身可能成为瓶颈] → 报告给出吞吐与并发数，若吞吐远低于预期且错误以传输失败为主，需先排除施压端瓶颈。

## Migration Plan

- 全新模块与命令，既有行为不变。
- 回滚：移除模块与子命令即可。
