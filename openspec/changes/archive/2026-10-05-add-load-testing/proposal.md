# Proposal

## Why

平台能验证工具、轨迹、任务与回答质量，但没有回答「并发上来之后会怎样」。agent 服务与普通 HTTP 服务在负载下表现完全不同：单请求成本无上界、流式连接数不等于吞吐、第一个饱和点往往是外部模型的限额、限流触发重试再推高负载。用普通 HTTP 压测器施压，只会得到一个无法解释的 RPS 数字。

## What Changes

- 新增压测模块：按并发与请求总量（或持续时间）对 HTTP 目标施压，测量真实完成情况。
- 延迟同时给出 p50、p90、p95、p99；流式响应另外测量首字节时间。
- 支持从响应体按字段路径提取扇出与用量指标（LLM 调用数、工具调用数、token 数），并给出均值与 p95。
- 明确区分「未观测到扇出」与「扇出为零」：没有提取到数据时如实标注，不填零。
- 错误按原因分类：超时、限流、服务端错误、客户端错误、传输失败。
- 支持非功能预算：延迟上限、错误率上限、吞吐下限，超限即判不通过。
- 压测结果产出普通运行记录与指标，因此控制台与门禁零改动即可覆盖。
- **BREAKING**：无。新增命令与模块，不影响既有行为。

## Capabilities

### New Capabilities

- `load-testing`: 压测场景定义、并发施压、延迟与扇出指标采集、错误归因、预算判定与运行记录产出。

### Modified Capabilities

无。

## Impact

- 新增 `agenteval.load` 模块，承载场景模型、并发执行与指标汇总。
- CLI 新增 `load run` 子命令，支持用 `--base-url` 复用同一份场景指向不同环境。
- 压测结果写入既有运行记录，并填充标准指标字段，使控制台可直接展示。
- 依赖无新增：并发用标准库线程，请求用标准库 `urllib`。
- 本变更与既有 `usage-budgets` 的口径一致：成本与扇出按请求统计，而不是按整体粗略平均。
