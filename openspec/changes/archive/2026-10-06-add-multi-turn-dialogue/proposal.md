# Proposal

## Why

现有各层都建立在「一次性任务」上：`AgentRunner` 把环境与任务交给 agent，等它跑完，再读轨迹。真实运维场景却大量是多轮的——agent 需要先问清故障时间再查日志，用户会在中途补充信息或改口。这种场景里「它有没有先问再动手」「几轮之内收敛」根本无从断言，因为平台在 agent 执行期间拿不到控制权。

## What Changes

- 新增对话模型：带角色的回合序列，agent 回合可携带工具调用。
- 新增逐轮 agent 协议：agent 接收对话状态、返回本轮回复，循环控制权在平台手上。**这是新增协议，不改既有的 `AgentRunner`。**
- 新增用户模拟器协议与确定性脚本模拟器：按剧本逐句回复，剧本用尽即结束对话；LLM 模拟器留成可插拔。
- 新增对话运行器：驱动「用户开口 → agent 回复」的循环，受回合预算限制，并把每轮的工具调用归到该轮。
- 新增两类对话断言：先问后做（首次调用某工具之前 agent 必须问过某个标记）与收尾（最后一轮必须包含完成标记）。
- 回合预算本身也产出判据：自然收敛与预算耗尽能被区分。
- 结果产出既有运行记录与轨迹，因此轨迹类断言与门禁同样适用。
- **BREAKING**：无。既有一次性任务协议与所有接入方不受影响。

## Capabilities

### New Capabilities

- `multi-turn-dialogue`: 对话模型、逐轮 agent 协议、用户模拟器协议与脚本实现、对话运行器与对话级断言。

### Modified Capabilities

无。

## Impact

- `models.py` 新增对话用例与两类对话断言，并纳入用例联合类型；既有三类用例不变。
- 新增 `agenteval.dialogue` 模块与 CLI `dialogue run` 子命令。
- `ContractRunner` 增加对对话用例的显式拒绝，避免用错命令时静默失败。
- 依赖无新增；脚本模拟器是确定性的，不需要模型。
