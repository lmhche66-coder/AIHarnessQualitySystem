# Design

## Context

- 既有轨迹层（`process.TraceSession`）已经把工具调用写进 `Trace`，判定层（`check_process_case`）在轨迹上做过程断言。See proposal.md - Why。
- 上一轮新增了评测范围画像与三维记分卡（`profiles` / `scorecard`），模块级范围已存在，但缺「模块信号从哪来」与「模块断言怎么判」。
- 硬约束：平台不调用任何模型；模块信号必须由被测 agent 或平台侧适配器提供；新增字段与事件都要向后兼容。

## Goals / Non-Goals

**Goals:**

- 让 agent 用一条通道把四个模块的执行信息写进轨迹。
- 让模块级断言像既有过程断言一样，只依赖轨迹、可复现。
- 让一个模块的错误不污染其他模块的统计。

**Non-Goals:**

- 不插桩 agent 内部模块：平台不猜信号，缺信号就是缺信号。
- 不改工具调用断言的既有语义。
- 不引入外部模型或采样器。

## Decisions

### D1 模块信号以保留事件名落在既有 Trace 上

信号写成 `module.perception` / `module.planning` / `module.memory` / `module.retrieval` 事件，载荷是自由字典。不新增运行记录字段，因此历史轨迹、既有断言与持久化格式都不受影响。
备选：给 Trace 增加强类型节点（要改运行记录格式，且限制 agent 的表达）。

### D2 信号由 bridge 上报，平台只做采集

`BridgeResponse` 新增可选的 `signals`，agent 在响应里带上各节点信息，平台在用例执行期写入当前轨迹。与文章一致：信号产生在 agent 侧，平台负责采集与判定，不从回复文本反推。
备选：平台解析 agent 输出文本推断意图与路由（不可靠，且正是文章反对的做法）。

### D3 模块断言复用既有过程断言通道

五种新检查注册进 `_HANDLERS`，因此过程、任务、对话三条链路零改动即可复用。断言只读轨迹上的模块信号，缺失信号判为失败并给出可定位的原因。
备选：为模块评测单独做一套执行器（与既有链路重复）。

### D4 上游跳过做成判定后的后置规则

`apply_upstream_skip` 在所有断言产出后运行：只要路由决策断言失败，就把依赖检索证据的下游指标标记为跳过。这样修正不需要断言之间互相知晓，规则集中在一处。
备选：让每个下游断言自己检测上游结果（规则分散，容易漏）。

### D5 记分卡按指标归口聚合到模块

指标到模块的映射集中在 `modules.METRIC_MODULE`，记分卡据此产出 `modules` 分组。范围决定「评哪些数据集」，模块分组回答「哪个模块出问题」。
备选：按断言名猜测模块（名字一改就失效）。

## Risks / Trade-offs

- [agent 上报的信号可能不实] → 平台只负责一致性：断言比对的是 agent 自报的值，真实性由 agent 的接入方保证；这与文章一致。
- [信号缺失被当作失败] → 断言在缺失信号时给出明确原因，且沿用了既有的 fail 语义。
- [新增用量回写会多写一次运行目录] → 回写是幂等的整目录覆盖，代价可接受，换来用量不再丢失。

## Migration Plan

- 新增字段与事件都可选，既有 agent、用例与运行记录无需改动。
- 回滚：移除 `modules` 模块与五种检查、去掉 bridge 的 `signals` 字段即可。
