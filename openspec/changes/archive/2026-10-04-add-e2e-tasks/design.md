# Design

## Context

- 既有 `eval-core` 提供统一数据模型；`trace-assertions` 提供过程断言与轨迹归一化；`trace-persistence` 让轨迹可复用；`quality-gate` 消费运行记录做准入判定。See proposal.md - Why。
- 平台目前能回答「工具对不对」「过程对不对」，但回答不了「一批真实任务里做成了几件」。
- 硬约束：任务之间不能有状态残留，否则通过率本身就是噪声。

## Goals / Non-Goals

**Goals:**

- 任务可声明、可复现、可统计，通过率口径明确。
- 环境在每个任务开始前处于初始状态。
- 被测 agent 与任务定义分离，换 agent 不需要改任务。
- 任务结果直接进既有运行记录与门禁，不新增一套结果格式。

**Non-Goals:**

- 不做重复尝试与 pass@k 统计，本变更只统计单次执行的任务通过率。
- 不做环境快照与恢复，v1 用工厂重建达成隔离。
- 不做沙箱容器编排与浏览器/桌面驱动，环境的具体实现由使用方提供。
- 不做任务集的版本管理与失败样本回流。

## Decisions

### D1 任务定义与解法分离

任务只描述「要达成什么」，不包含 agent 的步骤；agent 通过统一协议接入。这样同一个任务集可以换不同 agent 跑，通过率才可比。
备选：把步骤写进任务（换 agent 就要改任务，通过率失去可比性）。

### D2 环境隔离用工厂重建实现，而不是快照恢复

每次执行任务前调用环境工厂构造一份全新环境。这是最彻底的隔离，不依赖工具实现是否支持快照，也不会因为漏还原某个字段而引入噪声。
备选：快照与恢复（需要每个工具支持，漏还原就是隐性污染）；进程级隔离（v1 复杂度不必要）。

### D3 成功判据复用过程断言，并新增终态断言

过程断言已经在 `trace-assertions` 中定义并实现，任务层直接复用；真正缺的是「最终状态对不对」，因此新增终态断言读取环境状态并与期望值比较。
备选：为任务单独定义一整套判据（与过程断言重复）；只判过程不判终态（无法回答任务是否真的完成）。

### D4 状态不可读取时判失败而不是崩遗

未注册工具、工具没有状态读取能力、字段不存在，都是任务配置问题。判失败并说明原因，才能让使用者一次看清问题出在哪，而不是拿到一个栈回溯。
备选：抛异常（会被上层收敛成 error，丢失「判据本身不可评估」与「agent 失败」的区分）。

### D5 agent 异常与判据失败分开

agent 抛异常记为 error（执行没走完），判据不满足记为未解决。两者的排查方向完全不同，混在一起会让通过率无法解释。
备选：都记为未解决（无法区分「没跑起来」与「跑了但没做对」）。

### D6 通过率以运行元信息承载，判定仍逐任务写入

每个任务产出一条普通 Verdict，通过率汇总写入运行元信息。这样门禁的阈值与回归判定无需任何改动就能覆盖任务运行，通过率则作为业务口径单独读取。
备选：把通过率塞进单条 Verdict（门禁语义被扭曲）；另建一套任务结果文件（重复实现汇总、存储与门禁）。

## Risks / Trade-offs

- [工厂重建可能比快照恢复慢] → 任务级隔离优先于速度；后续如成为瓶颈再引入快照。
- [单次执行的通过率对随机性 agent 不稳定] → 本变更明确只做单次统计，重复尝试与 pass@k 留给后续变更。
- [终态断言只能比较相等，表达力有限] → v1 刻意保持最小；需要区间或集合判断时再扩展判据类型。
- [任务集需要持续维护，成本是长期的] → 这是 L4 的固有成本，已在非目标中说明不做版本管理，避免假装它能自动解决。

## Migration Plan

- 新增能力与新增用例类型，既有用例与运行格式不变。
- 回滚：删除任务模块与 `task` 子命令，`models.py` 移除任务相关模型即可。
