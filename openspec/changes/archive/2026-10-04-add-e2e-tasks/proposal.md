# Proposal

## Why

前三层都在验证「工具对不对、过程对不对、门禁拦没拦住」，但没有任何东西回答业务方唯一关心的问题：一批真实任务里，agent 到底做成了几件。没有这个数字，前面的用例都只是内部质量指标。端到端任务成功率必须自建，外面的框架只能给任务定义与通过率口径的模板。

## What Changes

- 新增端到端任务能力：任务声明标识、描述与成功判据，平台提供可复现环境、调用被测 agent、评估成功并统计通过率。
- 环境由工厂构建，**每个任务开始前重建一次**，保证任务之间没有状态残留。
- 提供 agent 运行协议：平台把环境与任务交给用户提供的 agent，agent 的解法不写进任务定义。
- 成功判据由两部分组成：对执行轨迹的过程断言，以及新增的**终态断言**（比较环境中的实际状态与期望值）。
- 任务结果统计为通过率：已解决任务数除以任务总数，并分别列出未解决与出错的任务。
- 任务结果沿用既有 Verdict 与运行记录，因此质量门禁零改动即可覆盖任务成功率。
- **BREAKING**：无。既有用例类型、运行格式与门禁行为不变。

## Capabilities

### New Capabilities

- `e2e-tasks`: 端到端任务的定义、可复现环境生命周期、agent 运行协议、成功评估与通过率统计。

### Modified Capabilities

- `eval-core`: 统一数据模型中的评测用例需要增加「端到端任务」这一类，并校验其专属字段。

## Impact

- `models.py` 新增 `FinalStateCheck`、`TaskCase` 与任务检查联合类型，既有 `Case` 与 `ProcessCase` 保持不变。
- 新增 `agenteval.tasks` 模块，承载环境工厂、agent 协议、任务运行器与通过率统计。
- `fakes.py` 新增可观测状态的示例工具与任务用注册表工厂，既有 demo 注册表不变。
- CLI 新增 `task run` 子命令。
- 依赖无新增。
- 本变更是后续「重复尝试与 pass@k」「环境快照恢复」「失败样本回流」的基础。
